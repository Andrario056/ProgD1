3 Modelo entidad-relación

Seis tablas, un núcleo claro: centros y personas son el eje; vacunas alimenta dosis; y certificados_salud une persona, centro y dosis con uno o varios exámenes.

Leyenda: PK clave primaria · FK clave foránea · UQ único · JSON columna JSON. Las líneas indican relaciones 1 : N; las flechas no se dibujan para no saturar, pero la FK vive siempre en el lado “N”.
Relación circular: certificados_salud.examen_id apunta al examen principal y examenes.certificado_id apunta de vuelta al certificado. MySQL no permite FK diferidas, así que el modelo inserta primero el certificado con examen_id = NULL, luego los exámenes y al final actualiza el examen principal. Todo dentro de una transacción.
No dibujado para no saturar: dosis.centro_id, certificados_salud.centro_id y examenes.centro_id también referencian a centros. Es decir, un centro aparece en todas las tablas operativas.

5 Flujo: emitir un certificado con exámenes

Es la operación más delicada: toca dos tablas con una relación circular. certificadosSalud.crearConExamenes() la resuelve con una transacción: o se guarda todo, o no se guarda nada.

Por qué así: MySQL no admite claves foráneas diferidas. Insertar el certificado con examen_id = NULL rompe el círculo; luego se insertan los exámenes, que ya pueden apuntar al certificado; y al final se asigna el primero como examen principal.
Si algo falla: conexion.transaccion() ejecuta rollback() en el catch y libera la conexión en finally. El error se propaga a la ruta y esta responde con el estado HTTP adecuado. Nunca queda un certificado sin exámenes.
Después del commit: el modelo devuelve el certificado completo con sus exámenes mediante obtenerCompleto(), para que la interfaz no tenga que hacer una segunda consulta.

7 Ciclo de vida del certificado

El estado no es un cálculo de la interfaz: vive en la columna estado (ENUM('Vigente','Vencido')) y se actualiza en la base de datos.

Emisión emision y vigencia
→
Vigente estado inicial
→
Vencido cuando vigencia < hoy
Dos formas de llegar a “Vencido”: actualizarEstado(id, 'Vencido') para un caso puntual, o marcarVencidos(fecha) para actualizar en bloque todos los certificados cuya vigencia ya pasó. La ruta expone PATCH /api/certificados/marcar-vencidos.
Regla de integridad: el esquema exige vigencia >= emision. Un certificado no puede vencer antes de haber sido emitido.

Garantías del código

🛡️SQL parametrizado

Los valores viajan como ?. Los ORDER BY y LIMIT se resuelven con listas blancas y números validados.

🔁camelCase ↔ snake_case

La API usa primerNombre, centroId; MySQL usa primer_nombre, centro_id. El mapeo es automático.

🧩JSON automático

lotes y documentacion se aceptan como arreglos/objetos JS y se serializan al guardar.

📅Fechas estables

dateStrings: true devuelve YYYY-MM-DD, sin desfases de zona horaria.

⚠️Duplicados claros

Un ER_DUP_ENTRY se traduce a un error con codigo: 'DUPLICADO' para que la ruta responda bien.

🔒Transacciones

Las operaciones de varias tablas usan transaccion(): commit si todo va bien, rollback si algo falla.

📄Paginación acotada

limite se limita a 200 y nunca se concatena directamente en el SQL.

🧱Separación de capas

Las rutas no escriben SQL y los modelos no contienen lógica HTTP ni vistas.

🧪Validación doble

El modelo exige campos y coherencia; MySQL refuerza con FK y CHECK. La interfaz valida antes de enviar.

En una frase: las vistas capturan y muestran datos; las rutas traducen HTTP a llamadas de modelo; los modelos construyen SQL seguro y devuelven promesas; MySQL garantiza la integridad. Cada capa hace una sola cosa.
