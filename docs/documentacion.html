Sección 01

Visión general del proyecto

Salud Vacunas es una aplicación web estática con tres perfiles. No usa un framework de interfaz ni un servidor: cada vista es una página HTML independiente que carga JavaScript clásico y un CSS compilado.

Qué hace la aplicación

  • Perfil 1 · Centro de salud: registra usuarios y vacunaciones, con peso, altura, vacuna, lote y vencimiento.
  • Perfil 2 · Sub-región: consulta el historial de certificados médicos y permite registrar nuevos certificados.
  • Perfil 3 · Master: consulta la red completa: historial de vacunaciones, certificados, centros, perfiles y avisos.
  • Páginas públicas: inicio de sesión de demostración, recuperación de contraseña y verificación de certificados.

Cómo se abre

El punto de entrada es index.html. Se puede abrir directamente con doble clic; no hace falta instalar un servidor. La aplicación está pensada para funcionar con file://, por eso no usa módulos ES ni importaciones entre archivos JavaScript.

Importante: los datos que se crean mientras se navega no se guardan en una base de datos. Se guardan en la sesión del navegador y se pierden al cerrar la pestaña o el navegador. La base de datos solo está definida en esquema.sql; todavía no está conectada a la interfaz.

Qué significa que sea estática

  • No hay fetch a una API ni endpoints de backend.
  • Los datos de demostración están escritos en bloques ocultos dentro del HTML.
  • Los formularios leen y escriben en el DOM y en la sesión del navegador.
  • El CSS se compila con Tailwind CSS y daisyUI mediante npm.

Sección 03

Cómo se carga y se inicializa una página

Todas las vistas cargan los scripts en un orden concreto. Ese orden es importante: cada archivo depende de funciones que han sido publicadas antes en el espacio global window.Pro2.

Orden típico de scripts

<script src="../src/js/nucleo.js"></script>
<script src="../src/js/datos.js"></script>
<script src="../src/js/comun.js"></script>
<script src="../src/js/publico.js"></script>
<script src="../src/js/certificados.js"></script>
<script src="../src/js/app.js"></script>
ArchivoQué aportaSe necesita antes de…
nucleo.jsUtilidades, tema, sesión, alertas y constantes.Cualquier otro módulo.
datos.jsLectores de datos: usuarios, registros, vacunas, centros y certificados.Los módulos que consultan datos.
comun.jsFichas de usuario, esquema de vacunación y HTML de certificados.Consulta y certificados.

El atributo data-pagina

Cada <body> declara qué vista es. Por ejemplo:

<body data-pagina="centro-registrar-vacunacion">

app.js usa ese valor para buscar el inicializador correcto:

const paginas = {
  login: [Pro2.iniciarLogin],
  recuperar: [Pro2.iniciarRecuperar],
  verificar: [Pro2.iniciarVerificar],
  "centro-registrar-usuario": [Pro2.iniciarRegistroUsuario],
  "centro-registrar-vacunacion": [Pro2.iniciarVacunacion],
  "master-historial": [Pro2.iniciarHistorial],
  "master-certificados": [Pro2.iniciarHistorialCertificados],
  "master-centros": [Pro2.iniciarCentros],
  "master-avisos": [Pro2.iniciarAvisos],
  "subregion-certificados": [Pro2.iniciarCertificados],
  "subregion-certificados-historial": [Pro2.iniciarHistorialCertificados],
  consulta: [Pro2.iniciarConsulta]
};

document.addEventListener("DOMContentLoaded", () => {
  Pro2.iniciarNavegacion();
  const acciones = (paginas[document.body.dataset.pagina] ?? []).filter(Boolean);
  acciones.forEach((accion) => accion());
});

Sección 04

El sistema de datos con atributos data-*

Los atributos data-* son la columna vertebral del proyecto. Se usan como ganchos para JavaScript, como almacenamiento de datos de demostración y como configuración de cada página.

Cómo se leen desde JavaScript

Un atributo con guiones se convierte en una propiedad dataset en formato camelCase:

data-usuario-id      → elemento.dataset.usuarioId
data-dosis-esquema   → elemento.dataset.dosisEsquema
data-consultorio     → elemento.dataset.consultorio
data-campo-fecha     → elemento.dataset.campoFecha

Los atributos se pueden seleccionar con selectores CSS:

const formulario = document.querySelector("[data-form-vacunacion]");
const campo = formulario.querySelector("[data-campo-fecha]");

Los tres usos principales

1. Ganchos de comportamiento

No contienen datos de negocio: sirven para encontrar elementos y conectar eventos.

data-form-* data-campo-* data-tabla-* data-stat-* data-salir data-tema

Ejemplo: [data-form-vacunacion], [data-campo-vacuna], [data-tabla-historial].

2. Datos de demostración

Están dentro de contenedores ocultos y representan registros completos.

data-datos-usuarios data-datos-registros data-datos-vacunas data-datos-centros data-datos-certificados

Ejemplo: un <article data-usuario> con atributos de nombre, cédula, centro y datos de contacto. El peso y la altura se leen de cada registro de dosis.

3. Configuración de página

Indican contexto, comportamiento o alcance de la vista.

data-pagina data-inicio data-theme data-alcance data-placeholder

Ejemplo: data-alcance="red" en la consulta del Master.

4. Estado de controles

Algunos atributos se agregan o actualizan desde JavaScript.

data-tema-listo data-usuario-id data-lote

No siempre están escritos en el HTML inicial; pueden aparecer después de una acción.

Los bloques ocultos de datos

Los datos de demostración están en elementos con el atributo hidden. No se ven en pantalla, pero siguen en el DOM y datos.js los puede leer.

Cómo se publican las funciones

Cada archivo es una IIFE (función autoejecutable) que agrega sus funciones a window.Pro2. Así los demás módulos las pueden usar sin importaciones:

(function () {
  "use strict";

  const { $, esc } = window.Pro2;

  function hacerAlgo() {
    // ...
  }

  Object.assign(window.Pro2, {
    hacerAlgo
  });
})();

El archivo CSS fuente

src/css/estilos-fuente.css es la fuente que se compila. Contiene:

  • La importación de Tailwind CSS y el plugin de daisyUI.
  • Los temas salud (claro) y saluddark (oscuro).
  • La tipografía Inter Variable.
  • Los iconos SVG convertidos en máscaras CSS (.icono-*).
  • Estilos base, de componentes, de la barra superior y de impresión.
  • La regla que mantiene el certificado con fondo claro en modo oscuro.

El resultado compilado se guarda en assets/css/estilos.css. Las páginas cargan ese archivo compilado, no el fuente.

Comandos: desde la raíz del proyecto, npm run css compila una vez y npm run css:watch queda observando cambios. Si agregas clases nuevas de Tailwind en HTML o JavaScript, debes recompilar.
Sección 06

Cómo modificar apartados del código

Esta sección reúne los cambios más frecuentes y el orden recomendado para hacerlos sin romper la lectura de datos ni la inicialización de la vista.

6.1 Cambiar un texto o una etiqueta

  1. Busca el texto en el HTML de la vista.
  2. Si el texto se genera desde JavaScript, edita la plantilla correspondiente en src/js/.
  3. Si el texto está en una alerta o mensaje, revisa el módulo que llama a mostrarAlerta() o htmlAlerta().
Los textos visibles suelen estar en HTML; los mensajes dinámicos están en JavaScript.

6.2 Agregar un campo a un formulario

Ejemplo real: peso y altura en el formulario de vacunación.

  1. HTML: agrega el campo con un id, un name y, si el JavaScript lo necesita, un atributo data-*.
  2. JavaScript: obtén el elemento con $("[data-campo-peso]") y léelo en el submit.
  3. Validación: agrega las reglas antes de guardar.
  4. Persistencia: guarda el valor en el objeto o en la sesión con modificarSesion().
  5. Lectura: si el dato debe recuperarse en otra página, agrégalo al lector de datos.js.
  6. Visualización: agrega el dato a la ficha, tabla o tarjeta correspondiente.
  7. Estilos: si usaste clases nuevas de Tailwind, ejecuta npm run css.
<!-- HTML -->
<div class="flex flex-col gap-1.5">
  <label for="vacunacionPeso">Peso (kg)</label>
  <input id="vacunacionPeso" type="number" data-campo-peso />
</div>

// JavaScript
const campoPeso = $("[data-campo-peso]", contenedor);
const peso = campoPeso?.value.trim() ?? "";

if (!peso || Number(peso) <= 0 || Number(peso) > 500) {
  errores.push("El peso es obligatorio y debe estar entre 1 y 500 kg.");
}

6.3 Agregar o modificar datos de demostración

  1. Localiza el bloque oculto correcto: [data-datos-usuarios], [data-datos-vacunas], etc.
  2. Agrega un registro con un id único y todos los atributos que espera el lector.
  3. Si agregas un campo nuevo, actualiza el mapeo de datos.js.
  4. Duplica el bloque en todas las páginas que deban ver ese dato.
  5. Verifica que los nombres de atributos estén en kebab-case: data-dosis-esquema, no data-dosisEsquema.
<article data-vacuna
  data-vacuna-id="v-varicela"
  data-nombre="Varicela"
  data-tipo="Virus atenuado"
  data-procedencia="Internacional"
  data-dosis-esquema="2"
  data-cobertura="Capital,Central">
  <span data-lote data-codigo="VAR-2601" data-vence="2027-12-31"></span>
</article>

6.4 Crear una vista nueva

  1. Crea un archivo HTML dentro de la carpeta del perfil.
  2. Copia la cabecera y la navegación de una vista existente del mismo perfil.
  3. Incluye los scripts en el orden correcto, terminando con app.js.
  4. Asigna un valor único a <body data-pagina="mi-vista">.
  5. Agrega el inicializador en el mapa de app.js.
  6. Agrega el enlace en la navegación de las vistas del perfil.
  7. Incluye los bloques data-datos-* que necesite la vista.
  8. Actualiza index.html, README.md e INSTRUCCIONES.md si corresponde.
// app.js
const paginas = {
  // ...
  "master-mi-vista": [Pro2.iniciarMiVista]
};

6.5 Crear un módulo JavaScript nuevo

(function () {
  "use strict";

  const { $, $$, esc, mostrarAlerta } = window.Pro2;

  function iniciarMiVista() {
    const contenedor = $("[data-mi-vista]");
    if (!contenedor) return;
    // lógica de la vista
  }

  Object.assign(window.Pro2, {
    iniciarMiVista
  });
})();

Después incluye el script antes de app.js y registra el inicializador en el mapa de páginas.

6.6 Agregar un filtro al historial

  1. Agrega el control con data-filtro="nombreDelFiltro" o data-filtro-multiple="campo".
  2. Agrega la propiedad al objeto filtros de historial.js.
  3. Inclúyela en coincide() para que afecte la tabla.
  4. Inclúyela en el botón “Limpiar filtros”.
  5. Si es selección múltiple, usa opcionesMultiples().

6.7 Cambiar colores, tema o tipografía

  1. Edita src/css/estilos-fuente.css.
  2. Para el tema claro, modifica el bloque name: "salud".
  3. Para el tema oscuro, modifica name: "saluddark".
  4. Ejecuta npm run css.
  5. Recarga la página con Ctrl + F5.
@plugin "daisyui/theme" {
  name: "salud";
  default: true;
  color-scheme: light;
  --color-primary: #0066cc;
  --color-base-100: #ffffff;
  --color-base-content: #2c3e50;
}

6.8 Agregar un icono

Los iconos son SVG en base64 usados como máscaras CSS. Se declaran en src/css/estilos-fuente.css:

.icono-nuevo {
  --icono-url: url("data:image/svg+xml;base64,...");
}

Luego se usa en HTML:

<span class="icono icono-nuevo size-5" aria-hidden="true"></span>

6.9 Agregar un archivo descargable

  1. Coloca el archivo en assets/.
  2. Enlázalo con una ruta relativa correcta.
  3. Usa el atributo download si debe descargarse en lugar de abrirse.
<a href="../assets/afiche-certificado-medico.svg"
   download="afiche-certificado-medico.svg">
  Descargar afiche
</a>
Sección 07

Sesión, persistencia y modelo de datos

La aplicación no tiene backend. Los cambios de la sesión se guardan en sessionStorage y, como respaldo para file://, en window.name.

Funciones de sesión

leerSesion()       // devuelve el objeto de sesión o null
guardarSesion(obj) // guarda el objeto completo
modificarSesion(fn)// lee, modifica con fn y vuelve a guardar
cerrarSesion()     // elimina la sesión

Cómo se combinan los datos

// datos.js: ejemplo simplificado
const base = $$("[data-datos-usuarios] [data-usuario]").map(...);
const sesion = leerSesion();
const nuevos = sesion?.usuariosNuevos ?? [];
const medidas = sesion?.usuariosMedidas ?? {};

const combinar = (usuario) => ({
  ...usuario,
  ...(medidas[usuario.id] ?? {})
});

return base.map(combinar).concat(nuevos.map(combinar));

El resultado es siempre una lista combinada: primero los datos de demostración y luego los datos nuevos de la sesión. El peso y la altura de cada aplicación viajan dentro del registro de la dosis.

El tema se guarda aparte en localStorage con la clave pro2-tema, porque debe conservarse entre páginas y visitas. Los datos de negocio usan sessionStorage.

Qué se pierde y qué se conserva

  • Al cambiar de página dentro de la misma pestaña, la sesión se conserva.
  • Al cerrar la pestaña o el navegador, la sesión se pierde.
  • El tema claro/oscuro se conserva en localStorage.
  • Los datos de demostración siempre vuelven al abrir de nuevo.
Sección 08

Relación con esquema.sql

esquema.sql es el esquema relacional del sistema, pensado para PostgreSQL. No está conectado a la interfaz: es la definición de la base de datos que se usaría en una versión con backend.

EntidadColumnas claveRelaciones
centrosid, name, tipo_centro, autorizado, estado, municipio, parroquia, dirección, teléfonoLa subregión es un centro con tipo_centro = 1. Cada persona y cada dosis se vinculan al centro donde se atienden.
personasid, primer_nombre, segundo_nombre, primer_apellido, segundo_apellido, cédula, nacimiento, sexo, teléfono, correo, región, dirección, tipo_sangre, alergias, centro_id, registrado_porPertenece a un centro y, a través de él, a una subregión.

dosisid, persona_id, centro_id, vacuna_id, vacuna, tipo_vacuna, procedencia, lote, lote_vence, cantidad, peso, altura, dosis, fecha, aplicador, cargo_aplicador, atenciónRegistra cada vacunación aplicada a una persona en un centro. peso y altura son las medidas tomadas en esa aplicación y con ellas se calcula cantidad. vacuna_id apunta al catálogo; vacuna, tipo_vacuna y procedencia conservan la copia del momento de la aplicación.
certificados_saludid, código, persona_id, centro_id, dosis_id, examen_id, estado, emisión, vigencia, examen_fecha, bioanalista, médico, emisor, observaciones, sello, firma, documentaciónSe relaciona con personas, centros, dosis (dosis principal) y examenes (examen principal). El detalle completo de exámenes queda en examenes.certificado_id.
examenesid, certificado_id, centro_id, fecha, tipo, descripción, resultado, unidad, referenciaPertenece a un certificado y a un centro; representa cada prueba realizada y guarda su fecha y resultado.

La columna centros.tipo_centro usa cuatro valores enteros: 1 Subregión, 2 CDI, 3 Módulo y 4 Hospital. La columna centros.autorizado indica con TRUE o FALSE si el centro está autorizado para operar.

Los cuatro campos de nombre de personas (primer_nombre, segundo_nombre, primer_apellido y segundo_apellido) son obligatorios en todos los formularios de registro. La columna registrado_por guarda quién realizó el registro.

Todas las columnas de datos de las seis entidades son obligatorias (NOT NULL). La FK del examen principal es diferida (DEFERRABLE INITIALLY DEFERRED), porque certificados_salud y examenes se referencian mutuamente. Los centros con registros asociados no se pueden eliminar mientras esos registros no se reasignen.

La entidad vacunas define cada vacuna del catálogo: nombre, tipo, procedencia, laboratorio, descripción, meses para el refuerzo, obligatoriedad, dosis obligatorias y lotes disponibles. dosis.vacuna_id la referencia y los campos de texto de dosis conservan la copia histórica del momento de la aplicación.

La columna certificados_salud.documentacion exige un arreglo JSON con al menos un documento, y la columna dosis.lote_vence no puede ser anterior a la fecha de aplicación.

El peso y la altura se guardan en cada fila de dosis, no en personas, porque corresponden al momento de la aplicación. La cantidad aplicada se obtiene con la superficie corporal de Mosteller: √(peso × altura / 3600), escalada respecto a 1,73 m². El aplicador escribe la cantidad de referencia y el formulario muestra la cantidad calculada antes de guardar.

En una versión con backend, los lectores de datos.js se reemplazarían por llamadas a una API y los formularios enviarían los datos al servidor. La estructura de las vistas y los atributos data-* podría mantenerse casi igual.

La interfaz estática conserva algunos atributos de demostración que no existen como columnas en esquema.sql: data-dosis-esquema, data-cobertura y data-registrado-por-cedula. Son metadatos de las vistas de ejemplo; la base de datos no los almacena.

Sección 09

Errores frecuentes y lista de verificación

Antes de dar por terminado un cambio, revisa esta lista. La mayoría de los problemas del proyecto vienen de la carga de scripts, de datos que faltan en la página o de clases de Tailwind sin compilar.

Errores frecuentes

SíntomaCausa probableSolución
La página no reacciona.data-pagina no coincide con app.js o falta el script del módulo.Revisa el valor del body y el orden de scripts.
No aparecen datos.Falta el bloque data-datos-* en esa página.Duplica el bloque oculto en la página.
Un campo nuevo no se guarda.No se leyó en el submit o no se agregó al objeto/sesión.Agrega la lectura, validación y persistencia.
El dato se guarda pero no se ve en otra vista.Falta agregarlo a datos.js o a la función de renderizado.Actualiza el lector y la plantilla visual.
Los estilos nuevos no se aplican.No se recompiló el CSS.Ejecuta npm run css.
Los cambios desaparecen al recargar.Se guardaron solo en memoria y no en la sesión.Usa modificarSesion().
Una imagen o un enlace no carga.Ruta relativa incorrecta.Revisa ../ según la profundidad de la página.
Se ve HTML roto o texto raro.Datos sin escapar en una plantilla.Usa esc() antes de interpolar.

Lista de verificación

  • El HTML tiene etiquetas label asociadas a sus campos.
  • Los id son únicos dentro de la página.
  • Los nombres de atributos data-* están en kebab-case.
  • El body tiene el data-pagina correcto.
  • El módulo de la vista está incluido antes de app.js.
  • Los bloques de datos necesarios están en esa página.
  • Los datos nuevos se guardan con modificarSesion().
  • Los textos dinámicos usan esc().
  • Se ejecutó npm run css si se agregaron clases.
  • Se probó en modo claro y oscuro.
  • Se probó en pantalla grande y en móvil.
  • No hay errores en la consola del navegador.
